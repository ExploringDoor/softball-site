## CRITICAL

### C1. Live MailerLite API token hardcoded in admin.html (~line 9004)
A full, effectively non-expiring MailerLite bearer token is embedded in
`admin.html`. That file is served as static text — the client login only
hides the UI, not the source. Anyone who views-source / curls
`dvsl.vercel.app/admin.html` gets a token that can read your entire
subscriber list (~300 names + emails), delete subscribers, or send email
blasts from your verified sender.
**Fix:** Rotate the token NOW (treat as compromised). Move stats/list/blast
to a server function holding the token in a Vercel env var (extend
`api/mailerlite-subscribe.js`), gated behind real auth.

### C2. The push/admin secret ships to every browser (config.js line ~75)
`push.adminSecret: 'dvsl-push-2026-rkj3849f'` loads on every page. It's the
ONLY thing gating the write APIs. Because it's public, anyone can:
- `POST /api/update-firebase` → rewrite any game's score, mark done, mutate
  team W/L/standings, create player docs.
- `POST /api/send-notification` → mass-push all ~300 users + write inbox
  cards with attacker-controlled text/image.
- `POST /api/update-player` / `delete-by-source` → change/delete records.
No account needed — just the header value that's in the page source.
**Fix:** A secret that must reach the browser can't authenticate a
privileged action. Replace with a Firebase Auth ID token verified
server-side (Admin SDK) + an is_admin/captain claim check. Rotating alone
doesn't fix it (new value still ships to clients).

### C3. Three write APIs fail OPEN if the env var is unset
`api/update-firebase.js`, `api/update-player.js`, `api/delete-by-source.js`
use `if (SECRET && header !== SECRET) return 401` — so if
`ADMIN_SEND_SECRET` is ever empty (fresh deploy / rotation / accidental
removal) the check is skipped entirely and the endpoints are world-writable
to games/teams/players with no credential.
**Fix:** Fail closed like `send-notification.js`:
`if (!SECRET) return 503; if (header !== SECRET) return 401;`.

### C4. Unauthenticated destructive tool pages are deployed to prod
These git-tracked files are reachable by URL, have no login, and run
destructive Firestore deletes/writes on the live project:
- `firebase-cleanup-players.html` — deletes players
- `firebase-cleanup-boxscores.html` — deletes box scores
- `firebase-load-schedule-2026.html` — batch-wipes + reloads the schedule
- `firebase-team-setup-2026.html`, `firebase-add-games.html`,
  `firebase-add-rosters.html` — bulk writes
- `dvsl-admin.html` — a superseded OLD admin panel with full write access
  and NO login (unlike the current admin.html)
Nobody links to them, but a guessed URL is all it takes. Only your
Firestore rules stand in the way (not in the repo → unverifiable).
**Fix:** Delete them, or move out of the deploy root / add `.vercelignore`.
Also delete `post_p1.json` (a scrape from a different league) and
`can-delete-later/` (old index.html backup).

### C5. Captain re-submitting their own box score wipes the OTHER team's stats
`submitBoxScoreUnified` (captain.html ~4705, mirrored in profile.html):
the first branch does a full `setDoc` (document replace), not a merge, when
`first_submitter === myRole`. A captain's payload only contains their own
side's lineup. So: away captain submits → home captain submits (both sides
now stored) → away captain re-opens to fix a stat and submits again →
**setDoc replaces the whole doc, home_lineup reverts to empty.** The home
captain's batting + pitching stats are permanently gone, with a SUCCESS
toast and no recovery source. This is a supported flow (self-correction was
built intentionally), so it's a live data-loss path — and it's exactly what
the new "Only My Team" work makes more likely.
**Fix:** In the first branch, merge (preserve the other side's
lineup/pitchers/score/flags) or convert to an updateDoc that only writes
myRole's own fields — mirror the second branch.

## HIGH

### H1. Ties are split across two fields (`t` vs `ti`) AND dropped by two recalcs
- `admin.html` reads/writes ties as **`t`**; public `index.html` +
  `profile.html` read/write **`ti`** — different Firestore fields. An
  admin-side recalc writes `t`, which the public standings ignore → tie and
  its 2 points vanish publicly.
- `captain.html` and `scorer.html` `recalcStandingsFromAllGames` have NO tie
  branch (`as===hs` → nothing happens): no W, no L, `ti` never written, and
  the game is dropped from games-played + streak. A captain submitting a
  score runs this recalc and **erases ties from the standings.**
  Streak also corrupts (W, tie, W → renders "W2").
This is the "ties never recorded" bug from the April report, regressed in
two files. It matters now — you just had a BA@CHA 10-10 tie.
**Fix:** One shared recalc: single tie field (`ti`, to match the public
page), handle `as===hs` (ti++, streak break), consistent ppd/null guard,
one PCT rule. Call it from all four entry points (admin/profile/captain/
scorer).

### H2. Any authenticated user can seize any team's captain dashboard
(Known — CAPTAIN_TEAM_SWITCH_TODO.md, still unfixed.) `_writeCaptainClaim`
unconditionally writes `captain_claims/{teamId}__{uid}` with no allowlist /
approval. A captain (or any self-registered player) can Change Team → pick
any team → "Continue as…" → land in that team's dashboard (roster, chat,
schedule, score submit). In-code error strings confirm Firestore rules
currently permit these client writes.
**Fix:** Per the TODO — move claim writes to a server endpoint checking an
admin per-team allowlist; deny client writes to captain_claims in rules;
refuse unclaimed non-allowlisted teams in the auth screen.

### H3. Stored XSS via player name on public pages
`profile.html submitAddSelf` writes `name` verbatim (any self-registered
user), and `index.html` interpolates `${p.name}` into innerHTML in ~6 public
spots without the `esc()` helper it already has. Self-added players appear
in public stats immediately (`active:true`, `pending_approval` not
filtered). A malicious name payload executes for every visitor — and could
exfiltrate a commissioner's admin session token.
Same issue in the admin subscriber list render (unescaped MailerLite
`name`/`team`/`email`, which are injectable via the open subscribe API).
**Fix:** Wrap every user-derived interpolation in `esc()`; sanitize names on
write; filter `pending_approval` out of the public PLAYERS array.

## MEDIUM

### M1. OBP drops SF after a data refresh (index.html ~4630/4704)
Initial load computes OBP = (H+BB)/(AB+BB+SF); the post-refresh aggregation
never accumulates `sf`, so it flips to (H+BB)/(AB+BB) — a player with sac
flies shows a different (inflated) OBP/OPS after any refresh than on load.
**Fix:** Add `sf:0` to the refresh-path batMap init and accumulate it.

### M2. Captain-entered pitchers carry no W/L/SV decision
`readPitchers` (captain.html) returns no `decision` field; the aggregator
only credits wins/losses/saves from `p.decision`. Since the captain portal
is the main entry path, pitcher W-L-SV records are effectively empty for
most games (ERA/WHIP/IP/K are fine).
**Fix:** Add a W/L/SV selector to the captain pitcher form, or derive from
the final score for the starter, or hide pitcher W-L until there's a source.

### M3. Unauthenticated cost/spam endpoints
`api/parse-boxscore.js` (burns your Anthropic quota / free Claude proxy),
`api/notify-admin.js` (unlimited emails to you / Resend quota),
`api/mailerlite-subscribe.js` (injects arbitrary subscribers → feeds the
admin-list XSS). None are gated or rate-limited.
**Fix:** Gate behind real auth once C2 is addressed; add rate-limiting.

### M4. Hardcoded '2026' breaks the "next game" banner + countdown in 2027
`initNextGame` finds the game with a dynamic year, then displays
`date + ', 2026'` and feeds that to the countdown → in 2027 the banner
shows 2026 and the countdown reads all zeros. Several other spots gate
current-vs-historical on the `'2026'` literal.
**Fix:** Use `LEAGUE_CONFIG.season.year` everywhere the current-season year
is needed.

### M5. captain.html / player.html hardcode Firebase config
Instead of reading `LEAGUE_CONFIG.firebase` like the other 9 pages, these
two active pages inline their own Firebase block. Rotating the project or
cloning the repo for a new league would leave them silently on old creds
(the "clone Firebase gotcha").
**Fix:** Point both at `LEAGUE_CONFIG.firebase`; drop live-score.html's
duplicate inline block.
